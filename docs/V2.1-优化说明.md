# V2.1 优化说明

## 1. 评测从“找到数字”改为“完整结果等价”

旧逻辑把所有 SQL 的所有结果值并成集合。例如正确答案是 3，错误查询返回 1、2、3，也可能通过。现在从最后一条已执行工具消息提取结果，只比较该次查询与参考 SQL 的完整结果，检查列数、行数、重复次数、NULL，按题目决定是否检查顺序。数值允许 0.000001 的绝对误差，文本保持严格匹配。失败或截断结果不能通过。

30 个案例是不同关系查询场景，没有用大量同义问法凑数量。固定数据加入重名、无订单、零金额和固定日期，能暴露按姓名错误合并、LEFT JOIN 计数错误和时间边界错误。CI 不消耗模型 API；真实模型评测单独运行，输出三种检索模式的报告。

相关文件：`eval.py`、`evaluation/`、`tests/test_evaluation.py`。

## 2. 安全策略下沉到执行入口

字符串黑名单无法理解 SQL。例如字符串常量中的 DELETE 应合法，而带写操作的 CTE 应拒绝。现在 PostgreSQL 方言解析后只允许单条 SELECT 或集合查询，递归检查 AST，并校验实际数据源、别名、CTE 和字段。星号按授权字段展开，防止新加敏感列被自动暴露。函数采用允许列表，拒绝休眠、文件读取和会话配置函数。合法函数需明确加入策略，默认拒绝未知能力。

`execute_query` 和 `arun_sql` 在获取连接前校验 SQL。LangChain、MCP、CLI 及评测参考 SQL 都走相同策略。数据库账号只授予 users/orders 的 SELECT，真实数据库测试证明即使关闭默认只读设置仍不能 DELETE。只读事务、语句超时、服务端游标、行数和字节限制继续作为独立防线。

取舍：当前授权 Schema 显式维护，适合演示项目；增加表时需要同步维护授权和角色权限。RAG 索引连接与业务查询连接分离，但默认索引账号仍是演示所有者；部署时可再细分索引维护与检索角色。本版本没有加入业务身份、租户隔离或行级权限。

相关文件：`sql_policy.py`、`db.py`、`tools.py`、`mcp_server.py`、`db_init/reader.sql`。

## 3. 检索围绕“查对表、补齐关联”优化

原来动态 Schema 全部装在一份文档，表多后既难精准召回，也会浪费上下文。现在每表独立文档，加入真实类型、注释、主键和外键定义。关键词检索对中文使用双字片段、对英文使用标识符词项，与向量候选采用 Reciprocal Rank Fusion 融合，避免直接混用不可比的分数。再补齐候选表及一跳外键关联表的结构，降低缺少 JOIN 信息的概率。

这是简单、可解释的词项匹配，不是 BM25，也没有引入学习式重排模型。关键词候选来自进程缓存的文档目录，适合当前小规模授权 Schema；大规模时应换成数据库全文索引、专门检索服务或其他可扩展方案。

索引按稳定文档 ID 覆盖写入，以内容与元数据哈希判断变化；未变化文档不重新向量化，删除来源文档时同步清理向量。新集合独立于 V2.0，便于重建而不破坏旧索引。入库与在线检索应避免同时做结构性迁移，更新后重启 API 刷新目录缓存；当前没有实现跨进程原子版本切换。

相关文件：`rag/schema_docs.py`、`rag/ingest.py`、`rag/retrieve.py`。

## 4. 资源复用与异步调用

编译后的 LangGraph 和 LLM 客户端在 FastAPI 生命周期中创建一次，状态、计数和追踪留在每次调用里，避免请求间串话。Embedding、向量库和 SQLAlchemy 引擎分别复用；业务查询改用同步/异步 psycopg 连接池。并发上限提供明确的容量边界，超载返回 429。

图的异步路径使用 LLM 的 ainvoke 和 psycopg 原生异步 SQL，具备真实取消能力。Embedding 是本地同步推理，移到单独工作线程，取消等待时继续占用该工作槽位直到线程实际结束，避免取消风暴导致同时加载/运行大量模型。检索事务有数据库超时，应用退出会等待工作线程后再关闭索引资源。

连接池、缓存和并发限制均按进程计算，多 worker 部署需乘以进程数量。尚未做真实 LLM 服务压测，代码优化不能直接换算为吞吐提升比例。

相关文件：`api.py`、`db.py`、`graph/nodes.py`、`rag/embed.py`。

## 5. 执行预算、异常恢复与可观测性

工具调用预算在执行前检查，多个工具调用逐一计数。仅 SQL 执行阶段可修复的语法/字段错误允许有限修复，权限拒绝、查询超时和基础设施失败停止执行。AST 校验拒绝默认不可修复，避免模型反复尝试越权。每轮模型调用前后检查 usage 累计，并限制单次输出长度；总请求超时兜底 SDK 重试及外部等待。

WebSocket 使用 16 项有界队列形成背压；生产、发送、监听任务由统一监督循环管理。生产异常立即触发错误响应，断开、取消和超时都会清理所有任务并归还执行槽位。取消确认在实际任务回收后发送。业务查询取消通过 psycopg 传播到 PostgreSQL；集成测试检查取消后无残留活跃查询并可继续使用连接池。

节点追踪记录耗时、工具数、修复次数和 usage；API 返回 request_id 并输出结构化日志。最终回答前要求有成功且未截断的查询证据。不过“有证据”不等于“文字回答必然忠实”，目前还没有答案级独立评审器。模型供应商的计费终止也不受本地取消保证。

相关文件：`graph/state.py`、`graph/nodes.py`、`api.py`、`tests/test_api.py`。
